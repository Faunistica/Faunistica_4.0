# Итоговый отчет и рефлексия (Final Report)

## Итоговый вывод (MVP)
**Проект достиг состояния MVP**: пользователь может зарегистрироваться через Telegram‑бота, авторизоваться на сайте, заполнить и отправить записи, просмотреть статистику и выгрузить данные.

## 1. Статус готовности и сравнение с ТЗ
**Реализовано:**
- Регистрация пользователей через Telegram‑бота и вход на сайт.
- Веб‑форма для заполнения находок (гео, таксоны, материалы, замечания).
- Валидация данных и сохранение записей (autosave/submit).
- Экспорт данных в CSV.
- Общая и пользовательская статистика.
- Канал поддержки (форма + Telegram‑чат администратора).

## 2. Архитектурные и инженерные вызовы

**Вызов 1: Валидация сложных форм с разными форматами координат.**
- **Симптомы:** Пользователь вводит координаты в различных форматах
  (градусы/минуты/секунды). Ошибки формата приводили к некорректным гео-данным
  и невозможности геокодирования.
- **Исследование:** Проблема классифицирована как отсутствие единого слоя
  нормализации входных данных — каждый формат обрабатывался независимо,
  без общих правил валидации.
- **Решение:** Реализован единый слой преобразования DMS → десятичные градусы
  с правилами обязательных полей и детализированными ошибками валидации.

**Вызов 2: Конкурентные правки и стабильность данных.**
- **Симптомы:** При параллельной работе пользователь мог редактировать устаревшую
  запись, что приводило к потере данных.
- **Исследование:** Проблема классифицирована как Race Condition на уровне
  бизнес-логики — отсутствовала проверка актуальности версии записи перед
  сохранением.
- **Решение:** Реализовано обновление с проверкой версии (optimistic locking)
  и чёткая модель ошибок (stale record) с возвратом кода 409 Conflict клиенту.

**Вызов 3: Синхронизация состояния формы.**
- **Симптомы:** Форма заполнения находок содержит множество взаимозависимых
  полей. При навигации и перезагрузке страницы введённые данные терялись.
- **Исследование:** Отсутствовал механизм сохранения промежуточного состояния —
  форма работала только как единая транзакция отправки.
- **Решение:** Реализован механизм автосохранения (autosave) с периодической
  фиксацией состояния на сервере и восстановлением черновика при повторном
  открытии формы.

## 3. Организация процесса и командная динамика

- **Команда:** Проект выполнялся командой из 7 человек.
  - *Backend (Мальцев Е., Исаков Д., Мережко Г.):* Проектирование БД PostgreSQL,
    написание эндпоинтов на FastAPI, настройка Docker.
  - *Frontend (Полушкин М., Попов И.):* Вёрстка интерфейса,
    написание React-компонентов, связь фронтенда с API.
  - *DevOps (Авшарян Г.):* Docker-образы, production-деплой, настройка nginx.
  - *QA (Жданов Н.):* Разработка и проведение испытаний, реестр дефектов.
- **Процессы:** Задачи велись через GitHub Issues. Код хранился на GitHub.
  Использовалась модель ветвления: ветка `main` для стабильного кода,
  разработка велась в ветках `feature/*` с последующим слиянием через Pull Requests.
- Репозиторий разделён на `backend` и `frontend` с отдельными линт-процессами.
- Для качества кода предусмотрены линтеры и форматирование (Makefile-цели).

## 4. Рефлексия и приобретённый опыт

**Backend:**
- **FastAPI** — асинхронный REST API: dependency injection, middleware, фоновые задачи, lifespan-события. Впервые столкнулись с async/await на уровне веб-фреймворка.
- **Pydantic** — строгая валидация входных данных и сериализация ответов: custom validators, model_config, вложенные схемы.
- **SQLAlchemy 2.0** — ORM с аннотированной моделью данных: relationship, Mapped, составные запросы с оконными функциями для аналитики.
- **Alembic** — управление миграциями БД: автогенерация, ручные правки, добавление индексов и constraints в существующие таблицы.
- **aiogram 3** — Telegram-бот с FSM: сценарии регистрации, поддержка inline-клавиатур, middleware для фильтрации команд.
- **openpyxl** — экспорт и импорт записей в XLSX/CSV для научной обработки.
- **geopy / Nominatim** — обратное геокодирование координат в административные единицы.
- **SlowAPI** — rate limiting для защиты эндпоинтов от злоупотреблений.
- **pytest** — написание модульных и API-тестов с фикстурами и TestClient.

**Frontend:**
- **React 19** — компонентный подход: функциональные компоненты, хуки, контекст (FormContext) для глобальных данных формы.
- **JavaScript / TypeScript** — вся разработка велась на современном JavaScript (ES2022+) и TypeScript, с акцентом на читаемость и скорость разработки.
- **Zustand** — лёгкое управление состоянием формы без boilerplate.
- **react-hook-form + Zod** — производительная работа с формами: регистрация полей, кастомные валидаторы, синхронизация клиентских и серверных ошибок.
- **axios** — HTTP-клиент для запросов к API с перехватчиками для автоматического refresh JWT-токенов.
- **Tailwind CSS 4 + Radix UI** — адаптивная вёрстка и доступные headless-компоненты (Tooltip, Dialog, Select).
- **react-router** — вложенная маршрутизация, защищённые маршруты (PrivateRoute).

**Инфраструктура:**
- **Docker / Docker Compose** — контейнеризация и оркестрация сервисов (backend, frontend, postgres).
- **uv** — быстрый менеджер пакетов Python.
- **pnpm** — менеджер пакетов для фронтенда с жёсткими ссылками.

**Архитектурные практики:**
- **RESTful API** — проектирование ресурсных эндпоинтов, пагинация списков, partial-обновления через PUT.
- **JWT-аутентификация** — access + refresh токены, инвалидация по token_version, автоматический refresh на клиенте.
- **Optimistic locking** — защита от конкурентных изменений записей через проверку updated_at.
- **Darwin Core (DwC-A)** — работа с международным стандартом научных данных, отображение полей.
- **Finite State Machine** — FSM в aiogram для многошаговых сценариев регистрации и поддержки.
